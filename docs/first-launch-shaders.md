# 首次启动准备与预热八千个着色器

用户目标：从零构建 App，第一次启动就像已有游玩缓存一样，可以发现并预热约八千个着色器；不要求先进入游戏收集一遍。仅测试 Mac。

## 可选的异步绘制模式

启动界面的“异步着色器”复选框和 macOS 菜单栏“图形 → 异步着色器”控制同一项设置。
默认关闭；选择写入当前 `TOTK_PROFILE_DIR/graphics-settings.json`，保留同文件其他字段。
`TOTK_ASYNC_SHADERS=0|1` 可覆盖本次启动，供独立测试使用。

开启后可在首批预热尚未完成时继续启动；Metal 库和渲染管线未就绪时跳过绘制，后续帧重新检查，
编译完成后自动使用并记录到收集清单。相同着色器的预热和即时请求共用编译结果；后台即时库、
管线队列各限 64 个未完成任务，满时不阻塞绘制，后续帧再申请。关闭时加入已有任务并等待，
不会另编一份，也不会补做已经跳过的绘制。计算着色器与计算管线仍等待完成。

这是允许画面缺失的可选模式：物体、阴影、特效、全屏合成可能缺失或闪烁；有历史缓冲或写入副作用的
绘制被跳过后，影响也可能持续多帧。它不保证零卡顿；Switch 到 MSL 的新变体翻译及部分特殊函数构建
仍沿用同步路径。模式关闭时保留下文原有的全量首启预热要求，`verify_first_launch_shaders.py`
显式设为关闭以验证该要求。

`tests/test_async_compile.py` 用可控的编译门闩验证非阻塞返回、同键合并、队列容量与重试、关闭后等待、
失败终态和设置持久化。队列测试不启动游戏或 GPU，不能替代实际画面验证。

2026-10-18 实施验证：包含其他开发中改动的本地工作区通过 48 项源码测试；提取本功能并基于
上游 `41e1e0c` 的独立 PR 分支重新通过 39 项源码测试及修改文件的编译检查。两次独立 AppKit

### PR 审查修复

- iOS 的 `warm_filled` / `warm_light` 改用临时结果请求：同键仍合并正在编译的任务，最后一个调用者
  返回后移除仅供预热的任务记录。若实际渲染请求在途中加入，则保留该结果；已有常驻结果不会被预热淘汰。
- 预测管线的任务表检查异步缓存，避免关闭异步选项后重复编译。反向切换时也可非阻塞地查询已有预测任务，
  就绪后领用并归还槽位。两条路径的协调代码由渲染器和无 GPU 的模拟编译器测试共同使用。
- 实际 App 验证脚本在写入证据后、发送关闭命令前重新读取日志和检查抢占状态；检测到用户接管时，
  报告改为中断并保留窗口。无法读取本次运行日志时也不发出关闭命令。

专项回归覆盖 300 个临时结果的释放、途中加入的渲染请求共享结果、两个方向的开关切换，以及
日志写入期间用户接管/抢占、日志缺失、正常关闭及关闭超时。它们验证对象所有权和协调逻辑，
不代表已做 iOS 真机内存测量或新的完整游戏测试。

修复后独立 PR 分支的 49 项源码测试通过，修改的 Objective-C 文件编译检查通过。在项目外临时副本中
分别恢复结果长期持有、预测未去重、退出前未复检三种错误时，相应回归测试均按预期失败。
记录位于上述 `pr/` 目录的 `review-fix-tests.log`、`review-fix-compile.log` 和
`review-fix-negative-controls.json`。本轮没有替换本机已安装 App。

旧打包器只复制 PSO 标识清单，没有复制标识对应的 MSL、反射和依赖索引。空缓存实测预热为 0 个着色器，清单中有 2,171 个着色器标识缺少实际翻译数据。已有存档机器上的预热效果不能代表首次安装。

## 构建与启动行为

1. `build_app.py` 在签名打包前，用所选版本、已经通过完整校验的本地 RomFS 准备着色器，不读取现有用户缓存。`prepare_shader_seed.py` 解压字典压缩包，扫描全部 `Shader/` 包及 SDK/Bootup 包，解析支持的 BNSH/NVN 程序；不为旧式短 control 结构编造补齐字节。
2. 按运行时相同的 control + code SHA-256 去重，用原生翻译器和 SPIRV-Cross 生成默认绑定状态的 MSL、反射及依赖索引。成功准备少于 8,000 个时停止构建，不能只靠清单、重复条目或虚增计数交付。失败翻译留下的半成品不打包。
3. 生成 `build/shader-seed`。版本、翻译链、工具身份和所有文件哈希在复用/打包时检查；这是用户游戏衍生数据，保留在工作目录和 App，不提交源码仓库。Metal 库在目标 Mac 上生成，不打包其他 GPU 的二进制缓存。
4. 首次启动验证并导入到外部用户缓存，先发布 shader 文件，再合并 `.variants`；保留用户已有变体及其他文件。相同种子不重复导入，删除文件后可补齐；错误翻译链、篡改源文件和越界文件名被拒绝。并发调用等待同一次导入完成。
5. 已备好的整批 shader 在第一帧前预热。只把当前有数据的清单行算入进度，冻结本轮计划；缺源码的旧管线清单另行统计。新翻译的 MSL 只有在反射发布后才加入补充扫描，避免将仍在写入的配对文件误报失败。快捷键说明放在启动遮罩下面，预热过程中可以看见进度。

## 数量与范围

| 所选版本 | 独立着色器 | 离线翻译失败 |
|---|---:|---:|
| 1.0.0 | 9,360 | 0 |
| 1.1.2 | 8,286 | 0 |
| 1.4.3 | 8,290 | 0 |

这些是真实提取、翻译后的独立 shader，不是八千条管线，也不等同于某个存档曾经遇到的全部绑定状态变体。纹理类型、顶点属性和输出格式发生变化时，依赖匹配仍会拒绝不合适的种子并生成新变体；必要的验证不会为了命中率而省略。进入新场景仍可能出现管线及新变体编译，不能承诺消除所有卡顿。

1.4.3 种子约 334 MiB，24,871 个运行时文件。实际生产导入器的纯 CPU 对照：空目录导入 24,871 个文件，第二次导入 0 个，均识别 8,290 个 shader。源用户缓存、正式存档和其备份未用于生成这批数据。其他版本目前验证的是提取/翻译，不冒充新 App 的完整游玩验证。

首次试验的 86 个 system shader 是扩大范围前的中间方案；用户明确要求八千个后已替换为以上全量集合。早期测试因真实键盘输入停止了自动操作并保留窗口，不将中断的三轮脚本算作全部通过。中间打包还曾主动停止，用于修正快捷键面板遮住预热进度的问题；不把它当成最终版本。

## 复测

正常生成 App 使用 README 中原来的命令，无需新入口或手动 cache 参数。构建日志为 `<work>/logs/prepare-shader-seed.log`，首次启动日志应出现 `[shader-seed]`、实际数量、`启动关键管线已就绪` 和 `管线预热完成`；第一帧前种子必须全部可用。

完整诊断使用生产启动器、独立空 profile/翻译缓存和标准 game-slot，依次检查首次启动、相同缓存重开、关闭种子的空缓存负对照：

```sh
python3.14 games/totk/scripts/verify_first_launch_shaders.py \
  --app '/Volumes/mac-APFS/MacNativeGames-artifacts/apps/Tears of the Kingdom.app' \
  --output "$HOME/Library/Application Support/MacNativeGames/TOTK/tests/first-shader-check-new"
```

输出目录必须是新的；真实用户输入或用户新开游戏立即停止控制，保留测试局。已完成的启动阶段单独记载，后续截图/等待被中断不会改写成整轮通过。系统 Metal 驱动缓存不清除，因此该检查验证空翻译缓存的发现/预热行为，不能当成另一台全新 GPU 的冷编译耗时基准。

纯 CPU 导入诊断（不启动游戏或 GPU）使用 `scripts/diag/import_shader_seed.m`，链接 Foundation，包含 `third_party/d2r_gfx/gfx/nvn`。参数为包内 seed 目录及新的私有 cache 目录；连续运行两次应分别导入全部文件和 0 个文件。
